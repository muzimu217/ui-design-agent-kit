## 一、项目背景：AI 能写出界面，但没人能证明它做得对

2026 年的 UI 生成工具已经把"生成"做成了基础设施：一句话出页面、截图转代码、设计稿转实现。但当开发者真的把这些界面推向生产时，暴露出的不是"生成得不够快"，而是**"生成之后没有裁判"**。

本项目在立项前做过一轮小规模需求访谈（n=4 开发者，书面语料 28 条逐条编码），反复出现三类真实痛点：

1. **越权重写**——"我只想改一个按钮，它把整个布局重写了。"改动半径不受控。
2. **静默删边界**——"它把我的错误处理和空态判断删了，本地跑得好好的，上线就报错。"删除没有留痕。
3. **维护性焦虑**——"代码能跑，但我不敢动它，因为我不知道哪些是它猜的、哪些是我确认的。"

同期市场信号也在印证同一件事：头部生成工具的能力宣传几乎都集中在"更快出结果"，而对"结果凭什么算合格"普遍只有一句黑盒承诺（如"自动测试，减少 98% 错误"），既没有可查的测试清单，也没有谁签字的验收记录。**行业图谱里，生成层、模型层、托管层都已被占据，"验证纪律层"是空的。**

本项目的定位由此确定，并且此后所有迭代都围绕它：

> **不做生成引擎，做生成过程的监管与质量把控。**

## 二、技术架构

### 2.1 三层结构

| 层 | 内容 | 关键约束 |
| --- | --- | --- |
| **指令层** | 26 个技能（SKILL）组成的 UI 设计纪律：门径协议、排版军规、动效契约、文案契约、检测清单等 | 指令即产品；单文件提示词可导出，不依赖运行时 |
| **接入层** | 13 家宿主的一键接入（Codex、Claude Code、Cursor、Gemini CLI、GitHub Copilot、Windsurf、Cline、OpenCode、ZCode、DeepSeek Harness、OpenClaw、WorkBuddy、Hermes） | 一层转换、多宿主加载；宿主怎么换，工作流不变 |
| **验证层** | 六道门人工确认 + 五级证据等级 + 浏览器实测脚本 + 评测台账 | 每层都被 fixture 证明"能失败"，不是宣称 |

### 2.2 六道门：把"确认"变成不可跳过的停点

门径不是流程图，是**机械执行契约**——在任何会产生可视化产物的任务上强制生效：

| 门 | 名称 | 交付物 | 性质 |
| --- | --- | --- | --- |
| **A** | 方向稿 | 可指认的真实基线（URL + 借鉴点）+ 方向三旋钮 + 品味档案对照 | 用户裁决门（停止点） |
| **B** | 素材清单 | 素材来源、授权、替换方案 | 用户裁决门 |
| **C** | 原型 | 实质性新 UI 必须先出可点原型 | 用户裁决门 |
| **D** | 契约 | 设计契约：语义 token、动效参数、边界行为 | 用户裁决门 |
| **E** | 验收 | 六维实测回执 + 证据链 | 用户裁决门 |
| **F** | 留痕 | 调用记录与决策归档 | 留痕门（非停点） |

关键设计：**分级（S/M/L）只缩放产物深度，永不缩放门数**。一份简短方向稿也是方向稿；没有任何规模可以让"确认"这一步消失。

### 2.3 五级证据等级：区分"装上了"和"真的好看"

行业里最常见的偷换是：装了依赖就宣称"支持"，跑通脚本就宣称"验证通过"。本项目用五级阶梯强制区分：

```
Installed  ≠  Configured  ≠  Connected  ≠  Tool-callable  ≠  Visually Verified
```

只有当浏览器实拍 + 计算样式实测 + 键盘序列实测都通过，才能标记 `Visually Verified`。**没测的维度记 `—`，不计入分母，不虚记。**

### 2.4 可复核产物：工作台即证据

仓库内置的画布工作台不是营销页，而是**从仓库自身 JSON 数据计算出来的**证据面板：

- **产物墙**：每件产物带六维实测徽章（桌面/移动/键盘/对比度/降动效/控制台）、版本、来源（AI 直出 / AI+人工）、构建时缩略图快照
- **反例墙**：本项目自己的真实缺陷，只增不删（当前 6 条，全部已修复，`已删除：0`）
- **知识库**：12 张机制卡，按构成/运动/秩序三层归档，每张带可编码参数
- **能力登记**：11 项外部能力按四问契约登记（谁产出/边界/验收口径/证据），4 项已接入

## 三、应用场景

### 3.1 个人开发者：把口语需求变成可验收界面

```
安装 → 说需求 → 六道门逐门确认 → 浏览器实测 → 交付带证据的界面
```

门 A 强制先找一个**真实存在的成品**作基线（不允许"凭感觉设计"），门 E 强制交出六维实测回执。开发者拿到的不只是界面，还有"这份界面为什么合格"的完整记录。

### 3.2 团队：让 AI 改动有半径、有留痕

指令层内置改动半径纪律：改一处不许扩散到无关区域；删除必须显式说明；每次调用留痕。这让 AI 生成的代码从"能跑但不敢动"变成"可维护"。

### 3.3 任意 AI 宿主：一条纪律，多端一致

13 家宿主走同一条三层接入。团队换宿主、个人换工具，UI 设计纪律不随之失效——这是"工作流产品"与"某个工具的功能"的根本差别。

### 3.4 能力地平线：UI → 工作台 → 视频 → 3D

工作流不只覆盖网页。当前已把同一套证据纪律延伸到视频产物（Remotion + three.js 编码路径，165 秒产品片已上线），验收口径随形态定义（视频按确定性帧渲染验收，不套用网页六维）。

## 四、创新点

### 4.1 占据行业图谱的第四层：验证纪律层

对头部工具的持续对标（v0 / bolt.new / Lovable / Figma Make / Onlook / 国产三强等，累计 89 轮）显示：生成层、模型层、托管层均有强手，**验证纪律层长期空置**。本项目的六道门 + 五级证据 + 可复核产物墙是这一层的完整实现。

### 4.2 证据链可审计，且审计本身被审计

- 六维实测由脚本在真实浏览器里跑（WCAG 对比度计算样式、Tab 序列可达性、17 档宽度横向溢出扫描、控制台错误收集）
- 每个守卫都有**负向 fixture 自测**——证明它在该失败时确实会失败
- 反例墙记录本项目自己的事故（含一次"探测误报"、一次"断言未经实测"），只增不删

这一条是与其他"自动测试"承诺的分水岭：**别人承诺不犯错，我们公开犯错记录并证明修复。**

### 4.3 知识库驱动，而非提示词堆砌

12 张机制卡每张带可编码参数与适用边界，且能被脚本消费：音效卡 → 打点表（36 点三层，帧对齐 ≤2 帧机验）；时长矩阵卡 → 60 秒版时间轴契约（连续性/只裁不延/字幕边界七类断言）。**知识不是散文，落地即带断言。**

### 4.4 开源与可重建

Apache-2.0；`npm ci --ignore-scripts && npm run verify && npm test` 三步复现；画布工作台、离线复核包、视频工程全部可从源码重建，不依赖任何私有服务。
