## 二、调用链路审计（现状 → 不合理点 → 建议）

**现行链路**：需求 → SKILL.md（分类/边界）→ tool-routing（素材检索→候选
→门B）→ 设计契约（门A/门D）→ 原型（门C，禁代码）→ 实现（门F MCP 留痕）
→ 多轮验收（门E）→ 交付。证据侧：eval-run 台账（功能/样式分离）+ 
contrast 实测 + Playwright 取证。

| # | 不合理点 | 建议 |
| --- | --- | --- |
| L1 | **门上裁决堆积无消化机制**：9 轮冲刺累积 12 项待裁决，散落各文档，无汇总视图与超龄提示 | 建 `docs/gates.md` 门账本：条目=门/事项/提出轮次/状态；冲刺轮自动追加、用户裁决后销账（本轮报告第一节即手工版雏形） |
| L2 | **自动轮门B 策略模糊**：chain-flow 写「未选素材不得进入实现」，但 r3 实际走了「临时采用待追认」——规则与实践有字面冲突 | 在 chain-flow 明确：自动轮默认停门；仅仓库内部素材（无授权摩擦）允许先行采用并标「待追认」 |
| L3 | **evals 依赖 showcase/node_modules 软链**，verify 不校验该前提——showcase 清理则全部评测静默断裂 | verify.mjs 增加「软链有效性」检查（存在性 + 指向 showcase），断链时给出修复命令 |
| L4 | **e3 双轨未划界**：eval-e3.mjs（并行 WIP）与 eval-run.mjs 都围绕 scenarios.json，职责重叠风险 | 待 WIP 提交后统一口径：e3=盲评数据包、eval-run=执行台账（现状即如此，写进 quality-monitor 映射表即可） |
| L5 | **contrast 度量对与 PAIRS 手工维护**：token 改名会报错（好），但新增 token 不会自动进度量（盲区） | 可接受；建议在 DESIGN.md 质量门中约定「新 token 必须同步补 PAIRS 对」 |

## 三、结论

- 产品侧：7 项缺陷全部修复并复验；两产品功能与样式证据链完整。
- 链路侧：主干合理（门行为经 5 场景验证），主要短板是**裁决消化**与
  **依赖前提校验**，建议按 L1→L3→L2 顺序落地。
- 测试官自纠：本轮曾把 D3 误判为「脚本状态污染」，复验时纠正——
  误报要承认，真缺陷不放过。
