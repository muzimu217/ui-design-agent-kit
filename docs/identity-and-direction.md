# 项目定位与身份时间线（诚实交代：什么时候讲的是什么）

- 日期：2026-10-02 ｜ 状态：用户裁定后定稿
- 起因：外部批评（U-02，原文已随研究线存档于独立研究仓）质疑定位；用户 2026-10-02 裁定——**本仓库是"帮人类设计更好 UI 的智能体工作流"产品仓；研究是另一条架构线，当晚进一步裁定独立建仓（迁出本仓）**。

## 一句话定位

> **UI Design Agent Kit = 一个 UI 设计智能体 + 它的工作流**：通过 AI 调用技能（skills）、编排更好的工具（MCP/CLI/浏览器），把"一句口语需求"变成"有证据的可验收界面"——本质上是一个**用来生成更好产品工作流、并调度更优工具的智能体工作流**。

它不是研究项目本体。研究是**另一条架构线**——2026-09-30 曾入驻本仓，2026-10-02 已裁**独立建仓**（见文末）。

**专用性锚定（2026-10-11，用户原话）**：「我们这个 UI 设计，是专门为 UI 设计而设的。」本 Kit 是 **UI 专项**智能体——不做通用编码助手、不做全栈脚手架、不摊饼到非 UI 领域；技能路由、六道门与验收纪律全部围绕"界面质量"这一件事闭环。接入面再宽（13 宿主），专业纵深始终只有一条：UI 设计。

**生存位论证（2026-10-11 落地，源自妙多死亡复盘立卡）**：本 Kit 的生存位**不能是"又一个 UI 生成工具"**——生成赛道死亡名单反证其稀缺性：妙多 Motiff 功能栈齐全（AI 风格学习/指哪改哪/设计系统/MCP 代码交付）仍于 2026-07-31 停服，用户数据限期删除（docs/competitive-insights/2026-10-07-motiff/）。巨头的生态位碾压不认"你也很全"；无人占据的位置是**门+证据+实验级可审计**——这正是本 Kit 的唯一主张。

## 工作台形态与能力地平线（2026-10-19 方向裁定）

> 用户原话："更是一个工作台界面……去制作更好的界面，包括更好的艺术画面。不管是制作 3D 视频，还是用 AI 实时制作视频，还是通过代码，我们都是通过编码方式来进行实现的。通过大文本语与与大文本那种推理模型进行实现……界面设计、UI 设计、各种产品 UI 设计，还包括那个小游戏制作之类的，还有什么游戏 3D 渲染制作，我希望都能实现，通过这个 UI Agent。"

**形态升级（不是身份变更）**：产品从"智能体编排工作流（+附带画布页）"升格为**工作台界面（Workbench）即产品门面**——引擎仍是六道门工作流，工作台把引擎的**持久化状态与过程叙事**（task-state 阶段/门态、mission control 执行态×证据态、解析链路、产物墙、守卫回执）呈现为一等界面。持久化不再只是工程细节，而是工作台的产品特性（"持久化要使用"）。

**艺术画面为明示要求**：工作台及产物界面按 design-contract 品牌化升级（语义 token/动效弹簧/暗色高端视觉），"更好的界面，包括更好的艺术画面"是持续验收口径而非一次性任务。

**能力地平线（按序推进，一切经受控编码路径）**：

| 序列 | 能力 | 技术路径（编码） | 状态 |
| --- | --- | --- | --- |
| 1 | 网页 UI / 产品 UI 设计 | HTML/CSS/JS/React（既有六道门主线） | ✅ 已有 |
| 2 | 工作台界面升级（门面+艺术画面） | 画布工作台阶段 4（canvas-workbench-plan.md） | ▶ 当前主线 |
| 3 | 视频融合（AI 生成视频/实时视频制作） | Remotion/GSAP/HTML→video 受控编码链（remotion-video-agent 已在库内；hyperframes 学习结论已入账） | 排期中 |
| 4 | 3D 渲染 / 小游戏 / 游戏 3D 制作 | Web 编码路径（Canvas/WebGL/Three.js 类库）+大模型推理驱动 | 地平线 |

**边界保持**：不接第三方黑盒生成平台；不提供模型服务/账户/运行时；视频/3D/小游戏是"以编码方式的界面邻近扩展"（"因为本身就 UI，后续跟视频方面融合"），不是摊饼——每一序列仍走六道门+证据纪律，验收口径随形态定义（如视频产物按确定性帧渲染验收、不套用网页六维）。

## 能力接入与监管边界（2026-10-19 晚 用户定位再收窄）

> 用户原话："目前市面上产品越来越多了……我们就是制作工作流吧，**我们主打的是工作流**。但是相关知识库和 AI 功能让它进行接入就行了。比如说有个更好的图片生成 skill，或者是有个更好的那种 3D 模型建模 skill，可以接入我们的工作流进行生产产出。**我们解决的是个工作流问题，专注一下我们工作流的一个监管和产品质量把控**，这管把它做好。"

**一句话**：**本仓不做生成引擎，做生成能力的监管与质量把控层。**

| 层 | 谁做 | 本仓的角色 |
| --- | --- | --- |
| 生成能力（图像/3D/视频/模型） | 外部更强的 skill / 模型 / 平台 | **接入**，不重造；以适配器登记（谁、版本、能力边界、许可证） |
| 知识库 | 外部（设计系统/参考库/领域知识） | **接入并钉版**，作为门 A/B 的参考与契约来源 |
| **工作流监管** | **本仓** | 门 A-F 停点、证据分级、守卫（数据/渲染/分发三层）、六维验收、产物墙与对比 |
| **质量把控** | **本仓** | 契约先行（DESIGN.md/design-contract）、实测回执、检视级别如实标、不虚记 |

**由此产生的取舍（自我约束）**：
- 不因"市面产品更全"而扩张生成能力——**广度不是我们的战场，监管深度是**；
- 每个外接能力必须回答四问：①谁产出（能力名+版本）②边界在哪（能做什么/明确不能做什么）③如何验收（该能力专属的验收口径，不套用网页六维）④证据落在哪（路径+回执）。
- 外接能力的失败**必须如实记录**（不因"是别人的能力"而免责）；工作流对产物质量负最终责任。
- 契约文档：`docs/capability-adapters.md`；工作台界面登记：入口页"能力接入"区块（增量 30）。

## 是什么 / 不是什么（能力矩阵）

**是**：
- 一个项目级 UI 设计智能体：指令层（SKILL.md 体系 + 23 个技能）、有界工具编排（MCP 配置钉版）、六道门人工确认工作流
- 一套验证纪律：五级证据等级（Installed≠…≠VisuallyVerified）、131 项自动化测试（2026-10-08 全量口径：tests/ 122 + showcase/tests 9，计数由 doc-drift 锁定，以 npm test 实际输出为准；同日上午基线曾为 123=114+9，uak-init 补 8 例后为 131）、评测台账语料 157（2026-10-19 口径：…/豁免与增量/分镜与只读场景累计 +84）、已执行入账 71（2026-10-09 复核 evals/results.json；change-radius-discipline 等 4 条新入册待评）、浏览器实测强制
- 一个可迁移提示词工厂：`npm run prompt:build` 产出单文件提示词给其他宿主
- 12 个有独立 README/证据的线上案例

**不是**：
- 不是独立 AI 客户端/产品运行时（不提供模型服务、账户、付费素材）
- 不是运行时引擎/渲染框架（核心是智能体指令层+验证层，不假装有自动布局引擎）
- 不是 Figma 同步工具（设计源走 designContracts 品牌基线钉版通道，figma MCP 有意禁用）
- 不是 IDE 替代品（与 Cursor/v0 共存：本 kit 的价值在人机分工的确认门与证据纪律，不在生成能力本身）
- **不是研究项目本体**（research/ 是另一条研究架构线，见下）
