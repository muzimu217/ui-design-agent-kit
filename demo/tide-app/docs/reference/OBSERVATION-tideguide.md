# R3 浏览器实地观察记录（门B 要求 B2）

**观察时间**：2026-09-16
**观察方式**：真实浏览器（Playwright，1440×1000 视口）打开 https://tideguide.com/
**观察目的**：子代理 A 只确认了 HTTP 200 与标题，未亲眼看到曲线 UI。门B 裁决要求补齐实际观察。

## 一、观察到的内容

**页面结构**（首屏，不滚动）：

1. 顶栏：品牌标记 + "Help Center" + 蓝色 "Download" 按钮
2. **多设备产品图**：iPhone / iPad / Apple Watch 并排，屏幕内容都是潮汐曲线界面
3. 主标题：**"Know the forecast before you go."**（"forecast" 一词用蓝色强调）
4. 副标题：说明覆盖 Live tides / marine weather / clear forecasts，列出四个平台
5. 三个奖项徽章：Apple Watch App of the Year (Finalist)、Apple Design Award (Winner)、Editor's Choice
6. App Store 下载按钮

**关键观察：曲线在 iPad 屏幕里的呈现方式**

- 曲线**占据主视区**，横跨整个宽度，是界面里最大的元素
- 曲线下方是**渐变填充**（深蓝到透明），不是纯线条
- 曲线上标注了**高低潮时刻与潮位值**（如 "6:11p 7.1ft"、"12:00a 4.4ft"）
- 有一个**圆形游标点**停在曲线某处，旁边跟着读数
- 曲线下方另有一条**独立的细条带**，看起来是未来数日的潮差概览
- 整体配色：深蓝底 + 亮青曲线，与我们的方向高度接近

## 二、对方向的验证与修正

### 验证成立的部分

1. **"曲线即 hero" 成立** —— 这个产品的官网首屏不放海景照片、不放人物，放的就是曲线本身。我们的方向稿判断正确。
2. **深浅对比的用法成立** —— 深蓝底 + 亮色曲线，正是我们定的路子。
3. **高低潮时刻标注是行业惯例** —— 曲线上直接标时刻与数值，不是靠图例解释。

### 推翻我们假设的部分（重要）

**方向稿第三屏写"一日两次涨落的说明"，原意是用文字讲潮汐节律。观察到的事实是：这个产品的官网根本不解释潮汐原理。**

它的做法是：**用曲线本身承担全部表达**，配合一句"See the tide at a glance, then scrub through the curve"（一眼看懂，然后拖动曲线）。它默认访客已经知道潮汐是什么——因为目标用户就是海钓的人，他们不需要被科普。

> **结论：我们的第三屏"一日两次涨落的说明"是多余的，且带着说教气。** 目标用户是海钓/赶海的人，他们知道潮汐是什么。这一屏应当改为**展示曲线的实际用法**（例如"退潮前两小时最适合赶海"这类基于真实读数的判断），而不是解释潮汐原理。

### 一处我们做得更好、要保留的

**它的首屏只有产品图与 slogan，没有真实读数。** 门A 修正 A2 要求"第一屏不滚动即可见今日潮位读数"——观察确认这个要求是**我们的优势**，不是照抄。Tide Guide 的访客要滚动才知道今天潮怎么样；我们的第一屏直接给读数。
