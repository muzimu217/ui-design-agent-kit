## 一、总览

适用范围：下图是实质性新 UI 的流程，不用于把 kit 维护、只读评审或局部修复
升级成 demo/重设计任务。权限、续做时确认记录的复用和失效规则以
`ui-design-agent/SKILL.md` 为准。自检发现 P0 会阻断实现验收，不会授权修改
只读任务，也不会阻止交付一份明确列出阻断项的评审。

**任务分级（v7.1，D3 已定责）**：动手前随计划声明 S/M/L 级别，级别决定
走多少门（定义以 SKILL.md「Respect the assignment」为准）。**每个页面的
级别与边界必须由用户逐页明确确认，确认前不得走特批路径或缩减确认门**：

| 级别 | 定义 | 链路子集 |
| --- | --- | --- |
| S 窄修复 | 单组件/缺陷修复，无新方向、无新素材 | 不过门A-D；一轮有证据的验证（门E 单轮）；门F 按实际检查缩放 |
| M 页面级 | 新页面或成组新组件，方向已存在或影响小 | 门A-lite（一段方向 + 命名基线）；引入外部素材才过门B；门C-lite（基线截图/拼板可替代生图）；门D 按需；门E 全量多轮 |
| L 实质性新 UI | 新产品、多界面或品牌级方向 | 全链：门A-F |

窄修复不得借分级升级成重设计。

**细节级自我批评内环（v6，每道门呈现前强制）**：每一道门把产物交给用户
之前，先跑一遍 `references/detail-critique.md` 的内环——逐组件/逐交互按
维度评估（布局节奏 / 排版 / 对比度实测 / 状态覆盖 / 动效合规 / 可供性 /
鲁棒性 / 一致性）→ P0/P1/P2 严重度分诊 → 能自修的先修并复查 → 未修项带
严重度与原因随稿呈现。门是用户裁决**方向**的闸门，内环是 agent 裁决自己
**工艺**的闸门：能自己发现的错漏，不得留给用户在门上替你发现。

## 二、计划确认与一键执行

计划模式覆盖需求拆解、方向稿、素材候选和执行计划汇总。计划记录必须包含：
Mission、受众和主链路、范围与非目标、选定素材及授权边界、视觉/动效意图、
第一版原型 brief、目标视口、实现顺序和验收检查。记录格式与状态机见
`references/plan-execute.md`。

只有用户明确锁定某个计划 revision 后，执行请求才有效。执行请求会触发第一版
无代码原型并停在门 C；它不会自动通过方向、素材、原型、契约或成品验收门。
计划锁定后若品牌、范围、选定素材、原型 brief 或契约改变，计划必须标记 stale，
回到受影响的最早决策；单纯的实现缺陷可以保持计划锁定并走局部修复。

“一键执行”是一次明确授权的启动动作，不是跳过用户确认的快捷方式。

## 三、六阶段思维内核（设计师思维 ↔ 环节 ↔ 确认门）

流程的"闸门"是六道确认门，流程的"思维"是六阶段模型（完整模型与自我提问
清单见 `references/ui-designer-thinking.md`）。每个设计任务按阶段思考、按门
推进，不一口气跑完：

| 六阶段（思维） | 对应环节 | 出口确认门 |
| --- | --- | --- |
| 1 问题与目标定义（Why & What） | 环节 0-1 需求接收 / 初步设计稿 | 门A |
| 2 用户场景与链路分析（Who/When/Where） | 环节 1 初步设计稿（受众 / 主任务 / 入口出口 / 异常态） | 门A |
| 3 信息架构与层级（Structure & Hierarchy） | 环节 1 结构草案 + 环节 5 契约 | 门A + 门D |
| 4 视觉探索与规范（Visuality & Consistency） | 环节 2-4 素材/原型 + 契约风格基础 | 门B + 门C + 门D |
| 5 交互细节与落地（Interaction & Handoff） | 环节 6 代码开发（全状态 + 微交互 + 响应式） | 门E + 门F |
| 6 数据验证与迭代（Data & Iteration） | 环节 7 多轮交互动态验收（无线上数据时以用户确认为迭代信号） | 门E（每轮） |

阶段推进规则：逐阶段思考并咨询用户；阶段 5 代码开发前，阶段 1-4 必须已过
对应确认门；每个页面前过一遍自我提问清单（视觉焦点 / 可点击感 / 边界鲁棒 /
一致性 / 工程成本，各阶段另有专属问题）；每道门呈现前先跑细节级自我批评
内环（detail-critique.md：评估 → 分诊 → 自修 → 留痕）。

## 五、六道确认门（用户操作）

1. **门A 设计稿**（环节 1，强制）：主代理出初步设计稿（视觉基调、页面结构
   草案、动效意图，**不写代码**）发用户；用户看不通过就调整重发。
2. **门B 素材选择**（环节 3，强制）：候选素材清单发用户，用户勾选；
   **未选素材不得进入原型与实现**。
3. **门C 原型**（执行模式的环节 3，强制）：计划锁定并收到执行请求后，产出
   不写代码的原型（生成图或提示词生图）发用户；用户看不通过就调整素材/提示词
   或回到计划模式，不得直接写实现代码。
4. **门D 契约确认**（环节 5，大项目/动效复杂时强制）：DESIGN.md + 动效方案
   发用户确认。
5. **门E 每轮验收**（环节 7，多轮）：每轮走查后把"逐页动效/交互问题（每项
   带 P0/P1/P2 严重度与证据）+ 可替换的市面优秀产品/组件建议"发用户；用户
   勾选本轮修改项 → 修复 → 再走查；**直到用户确认通过**才进入交付；未修复
   的 P0 问题不得宣称完成。
6. **门F MCP 调用门禁**（环节 5/6/7，强制）：设计与实现阶段必须真实调用相关
   MCP 工具（Motion MCP 动效文档与 CSS 弹簧曲线、Context7/shadcn 组件与 API、
   Stitch 原型图、Playwright 浏览器证据），验收记录逐环节列出调用痕迹
   （服务器/工具/结果）；**无调用痕迹的实现不得宣称完成**；服务器不可用时
   如实记录尝试、失败与降级路径（详见 SKILL.md「Enforce MCP call gates」）。

规则：未过确认门不得进入下一环节；验收记录必须显示每个适用确认门已通过。
门上待裁决事项统一登记进 [gates.md](gates.md)（门账本）：停门前追加、裁决后
回填、P2 衰减与批量裁决规则见该文档；账本是门上事项的唯一权威记录。

## 六、初步原型（执行模式环节 3）三路径

原型阶段**禁止写代码、装依赖、启动开发服务器**，三种路径任选或组合：

- **路径 a（agent 生成）**：用用户选定的素材，调用生图能力或 Stitch MCP
  生成原型图给用户看（有则用之，无则降级到路径 b 或 c）。
- **路径 b（用户生成）**：agent 输出一份**生图提示词**（描述构图、风格、
  色彩、动效意图，可直接粘贴到 Stitch 网页版等工具），用户生成图片后给
  agent 看，agent 据此微调提示词或进入契约环节。
- **路径 c（成品截图拼板，v7.1 新增）**：生图不可用或不及时时，用真实
  浏览器抓取选定素材与可比成品的截图，拼成一页方向板；每张标注来源
  URL，全部是**参考数据而非可交付资产**。门C 裁决的是方向，不要求图
  必须是生成的——拼板与生图原型等效进门。

## 七、多轮交互动态验收（环节 7）

代码完成后不是单轮截图验收，而是**逐页、多轮、对照市面优秀产品**的验收：

- **每轮输出**：真实浏览器走查（键盘全旅程、点击、动效 normal/reduced/中断）
  后，生成**逐页清单**——每个页面列出：当前动效/交互问题（带 P0/P1/P2
  严重度与证据锚点）→ 优化建议 → 可替换的市面优秀产品/组件（来源 URL，
  来自灵感库与画廊）。出清单前先跑细节级自我批评内环（detail-critique.md），
  能自修的先修再列清单，未修项不得隐藏。
- **用户决策**：用户勾选本轮要执行的修改与替换项（也可要求替换为某个
  指定的优秀产品）。
- **执行**：一轮有证据的修复（优先复用市面优秀开源实现，走素材选择与授权
  核查，不主张"自己写的一定最好"）→ 再走查 → 下一轮。
- **终止**：用户确认通过，或明确说停止迭代。

## 八、动效规格与 MCP 调用点

| 动效类型 | 规格 | 实现能力 | MCP/工具调用点 |
| --- | --- | --- | --- |
| 交互反馈 | hover/press ≤150ms、spring 或 ≤150ms 过渡、禁 transition:all | motion/react 或 CSS | Motion MCP `generate-css-easing` |
| 动态流转 | 状态切换空间连续性（shared layout、AnimatePresence、级联 40-80ms） | motion/react | Motion MCP `search-motion-docs` |
| 背景动画 | 克制光影/网格/渐变流动，reduced-motion 降级静态 | CSS 或 motion/react | Motion 文档 + 浏览器证据 |
| 视频/时间轴（仅视频任务） | frame 时钟、确定性时间轴 | Remotion | `remotion-video-agent` + Remotion skills |

**边界**：网页动效走 Motion；Remotion 只用于视频/时间轴，不用于网页交互。

## 九、执行者分工

沿用 SKILL.md「Orchestrate agents」契约：主代理做 0/1/3/4(提示词)/7/8（分类、
设计稿、确认门交互、验收命令、交付）；子代理 A 做 2（检索）、B 做 5（契约）、
C 做 6（实现）。每环节执行者与每个确认门的通过情况必须写进验收记录。
