# 优先级建议（对话交付物全文 · e3-evidence-led-priorities）

## 先分档：三类输入的证据等级完全不同

| 输入 | 证据等级 | 能支撑的判断 |
| --- | --- | --- |
| 18/40 次提交前离开 | 观察计数，**未按设备/流量/失败原因细分** | 只知道"有流失"，不知道"为什么流失" |
| 客服记录：提交失败后已填内容丢失 | 单一来源，**未复现** | 值得核查的线索，不是事实 |
| 创始人希望加 3D 首屏动效 | 偏好表达 | 不构成用户价值的证据 |

**明确不说的话**：不能说"数据丢失导致了 18 次流失"——流失原因未细分，丢失报告未复现，
两者连相关关系都未建立；也不能承诺任何转化率或性能提升数字——没有测量就没有数字。

## 优先级判断：先花小钱核查数据丢失报告，再决定 PR 去向

理由：三个候选里，**「提交失败丢内容」是唯一可能任务阻断级的线索**（若为真，用户损失最大），
且核查成本最低（构造提交失败场景，检查本地态与表单内容是否保留）——在花掉唯一的小 PR
名额之前，先用一次便宜核查把它从"未复现线索"变成"已证实"或"已排除"。

## 小改动建议（有条件，bounded）

**若核查复现丢失**：一个小 PR——提交失败路径保留全部已填内容 + 明确错误提示（直述原因）。
**可证伪的验收检查**：构造提交失败（断网/非法响应两种），断言刷新与回退后表单内容完整保留；
任何一条失败即该 PR 不合并。

**若核查不复现**（连续构造均无法丢失）：该客服报告降级为"未证实"，小 PR 转向**流失细分
埋点**（按设备/流量来源/失败原因记录离开事件）——让下一轮的 18 次流失变得可解释。

## 关于 3D 首屏动效

当前证据不支持优先做：它与流失、数据丢失均无已建立的关联，纯视觉新颖性或权威偏好不是
排期依据。列为**待流失原因明确后按数据决策**的候选项——如果细分埋点显示流失集中在
首屏跳出，再评估它。
