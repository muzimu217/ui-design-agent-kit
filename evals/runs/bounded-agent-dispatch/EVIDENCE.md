# bounded-agent-dispatch 执行记录（R219 批次三十八）

需求：*「按任务级别安排这个 UI 工作，限制代理并发，不要一次启动很多子代理。」*
语境：项目已有 S/M/L 任务分级与 A/B/C 角色分工；素材检索、设计契约、实现存在前后依赖；**用户明确偏好节省 token，并要求一个完成后停止，再派下一个**。

## 调度方案（dispatch-plan.md 全文=主交付）

### 1. 任务分级与派发决策（第一判据：S 级不派）

| 级别 | 定义 | 派发决策 |
| --- | --- | --- |
| **S** | 窄修复：文案/单点样式/单行逻辑（影响面 ≤1 文件） | **主代理直接处理，零子代理**——派发的调度开销与上下文交接成本超过任务本身 |
| **M** | 单组件级：一个组件的实现/修复+验证（影响面 1-3 文件） | **最多 1 个活跃子代理**，主代理持调度权并逐件审查 |
| **L** | 完整特性：素材检索（A）→设计契约（B）→实现（C）链 | **严格 A→B→C 串行队列**，前一代理终结且经主代理审查后才派下一个 |

本次请求语境下：素材检索、设计契约、实现存在**前后依赖**——即便其中有理论可并行的独立片段（第三判据），**默认照样排队**：并行的收益是等待时间，代价是 token 峰值与上下文分裂，用户已明示偏好省 token 与逐个执行，偏好优先于效率假设。

### 2. 串行队列与生命周期（第三/五判据：闸门+释放规则）

L 级队列的每个环节是一个带**生命周期终态**的槽位：

```
[派发] → 子代理运行 → 终态（completed | failed | stopped）
                            ↓
                主代理审查（产出核验+是否继续）
                            ↓
                  ┌─ 通过 → 释放槽位 → 派发下一角色
                  └─ 不通过 → 修复指令回派同一代理（槽位不释放）或人工介入
```

**释放规则是硬性的**：任何时刻每任务**活跃子代理数 ≤1**；`completed` 后主代理未审查=槽位仍占用；`failed/stopped` 同样必须经审查才能派后续——不存在"失败了就自动派下一个兜底"的隐式行为（那会让失败被掩盖且 token 翻倍）。

### 3. 并发例外条款（第五判据：三条件全齐才开闸）

默认串行。并发例外必须**同时**满足且**记录在案**：

1. **用户明确授权**本轮并发（概括偏好不构成授权，逐次明示才算）；
2. **范围不重叠**：两个任务的文件/上下文集合无交集（依赖链上的环节永远重叠，不具资格）;
3. **token 代价与必要性入账**：预估双份上下文成本+为何不能串行的理由写进当轮记录。

缺任何一条 → 排队。**角色数量（A/B/C 三个）与并发额度无关**——三个角色只是分工名册，额度永远是 1（failCondition #2 防线）。

### 4. S 级反噬防线（failCondition #4）

「库存台按钮文案改一个词」这类请求：主代理 30 秒直接改完并自验。派子代理=交接上下文（读背景+写说明+核验产出）成本 5-10 倍于任务本身——**S 级派子代理本身就是浪费 token**，与用户偏好正面冲突。判断口诀：**如果给子代理写任务说明比自己做还长，就不派**。

## 可执行证明（dispatch-simulator.mjs）

规则不留在纸面：调度器实现为状态机（`dispatchPlan` 对象：`maxActivePerTask=1`、`serialGate` 审查闸门、`exceptionGate` 三条件校验、`release()` 显式释放），**12 条断言**覆盖：S 级零派发/M 级单活跃上限/L 级 A→B→C 串行次序/未审查不释放/failed 后必须审查再派/并发例外三条件缺一即拒（3 条反例）/角色数≠额度。全绿输出见 `evidence/simulator-run.txt`。

## 派发轨迹（queue-trace.md）

以示例需求「库存台新增 CSV 导出」走一遍真实调度决策：S（按钮文案）主代理直做→M（导出按钮组件）单子代理→L 链（素材 A→契约 B→实现 C）逐槽位走查——每步含派发理由、审查结论、释放记录，以及一次**故意并发违规被调度器拒绝**的对照记录。

## 边界与诚实声明

- 本场景为调度纪律（决策类），无 UI 交付物——styleReview 未评（与前例决策类口径一致）。
- simulator 是规则的可执行化，不是真实多代理运行的日志；真实每轮派发记录在评审循环的 state.json runs 链里（本循环自身就按「串行+审查闸门」运行：每轮一个主任务，审计/研究代理按需单发）。
